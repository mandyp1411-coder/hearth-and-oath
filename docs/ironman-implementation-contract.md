## Scope and non-negotiable behavior

- New lives explicitly opt into **Ironman (combat permadeath)**. Missing mode metadata means Standard. Existing Standard/legacy lives are never converted. Any present malformed Ironman metadata is rejected, not stripped or downgraded.
- The first positive-to-zero Health transition in a lethal battle kills that named participant permanently. Hero death ends the entire run immediately, including when an ally lives, the last enemy dies simultaneously, or an opening enemy turn kills the hero. Companion deaths apply even when the hero later wins or retreats.
- Verified supervised watchhouse bouts, explicitly supervised Paladin initiation and memory-only tactics rehearsal remain nonlethal. Enemy deaths, live captures/surrenders, temporary summons and previews are not party casualties. Natural mortality, ordinary retirement and natural dynasty succession retain current behavior; the run identity survives succession.
- Prehistory in `createLifeAtAge` remains Standard. Mode is attached only after a valid playable opening has been generated and immediately before its first guarded accepted save.
- This protects copies managed by updated code in this browser profile/origin. It cannot revoke external JSON, another profile/origin or old already-open application code. Copy never promises global deletion or anti-cheat.

## Exact state and combat interfaces

New pure module: `dist/js/ironman.js`. It imports neither engine, storage nor DOM. Combat, engine, save-store and app can depend on it without cycles.

Proposed game metadata (only opted-in lives have this property):

```js
state.ironman = {
  version: 1,
  runId: '<crypto.randomUUID or crypto.getRandomValues random identity>',
  startedDay: 6570,
  casualties: [{ personId, day, battleId, generation }]
};
```

`runId` is immutable, random and independent of seed/name/slot/revision. No weak random fallback for Ironman creation. `startedDay` and the run ID carry unchanged through successors. Casualties and the durable floor contain companion deaths only. Hero termination is derived from the validated terminal battle and independent ended marker, never a playable hero-dead snapshot. Companion casualties are unique by exact immutable lineage `personId`, monotonic and validated against the person's birth/death dates and snapshot day. A death of a prior generation stays attached to that old person even when a later generation reuses `mira`, `kest`, etc. No future dated casualties are injected into older states.

Proposed captured battle metadata:

```js
battle.mortality = {
  version: 1,
  runId,
  lethal: true, // false for an expressly supervised bout
  participants: [{ actorId, personId, kind: 'hero' | 'companion' }],
  deaths: [{ actorId, personId }]
};
```

Capture valid run identity, exact current lineage identities and lethality before `beginTurn` or opening enemy processing. The constructed non-ephemeral actor set must exactly match capture. Ironman Paladin initiation uses only the verified accepted engine context `{kind:'initiation',classId:'paladin',ownerId,locationId,oathType}` bound to the exact authored oath and pending class; other initiation routes remain lethal. Standard creates no new context. See the complete HP and encounter-policy inventory in `ironman-hp-mutation-inventory.md`. Resolve current companions by `source === 'companion' && localId === rosterId` in the current lineage, not the broad historical first-match `killNamedPerson` lookup. Hero identity is `dynasty.activePersonId`. Temporary actors have no participant entry. Existing Standard battle snapshots keep their rules untouched and no mortality metadata.

Pure module API to freeze in phase 1:

- `isIronman(state)`, `validateIronman(state)` and `createIronmanMetadata(state, cryptoProvider)`.
- `currentIronmanPerson(state, actorId)` and `captureBattleMortality(state, { nonlethal, solo })`; only verified watchhouse construction requests solo capture.
- `validateBattleMortality(battle, state)`, `sameBattleMortalityPolicy(before, after)` and `recordCombatZero(battle, actorId, previousHp)`.
- `ironmanBattleDeaths(state, battle)` returns new exact-person companion casualty records; `ironmanHeroDeath(state)` returns a validated terminal descriptor or null.
- `validateCasualtyFloor(state, floor)` rejects an omitted/conflicting/invalid death; `mergeCasualtyFloor(floor, state)` only adds exact validated deaths.

The terminal battle outcome is the new exact literal `ironman-death`, valid only with lethal captured Ironman rules, the same run/hero person identity, hero zero Health and a recorded hero death. It has null current actor and no later turn/reward/recovery. Existing Standard `defeat` and victory invariants remain unchanged. Mortality identity fields are immutable in `resolveBattle` comparison alongside existing captured ability fields.

Combat damage/self-cost/status paths record the zero transition at the actual decrement, not merely by comparing end-of-command Health. Recorded casualties cannot be healed/revived within the same battle. Hero terminal status takes priority over victory and stops later enemy actions. All HP mutation sites, including advanced-technique costs and damage/reflect/drain combinations, are included in the phase-1 inventory.

`createBattle`, `takeBattleAction`, `previewBattleAction`, encounter outlook and practice remain detached/pure. Engine acceptance boundaries apply casualty consequences to cloned game state after battle creation and accepted battle commands, including opening casualties. Companion application sets actual `alive=false`, `active=false`, `recruited=false`, HP zero, exact lineage deathDay and RPG stage `dead` together, preserving existing grief/relationship effects. Add an exact-person lineage death helper rather than alter ordinary broad lookup semantics. `resolveBattle` recognizes the validated terminal before any ordinary settlement. All engine actions that could continue a terminal run are rejected. Repeated mortality acceptance is idempotent.

Phase-2 implementation boundary: `beginBattle` first installs the actual battle, `instanceId` and trusted context, then validates and applies its exact companion deaths. `chooseBattleAction` applies new deaths on its detached accepted command result before personality/continuation. `resolveBattle` first performs the existing identity/actor/result checks, including immutable mortality policy, then accepts the completed battle and applies deaths before resource synchronization, rewards, time, recovery or encounter callbacks. An accepted hero terminal retains the internal captured battle descriptor, leaves the living hero record untouched, and returns before normal settlement. `killCurrentCompanionPerson` resolves the immutable current-person ID, uses the existing lineage death/grief mechanism, sets HP/RPG death state, and receives the matching companion ledger append within that same cloned acceptance boundary. A repeated accepted descriptor adds no ledger, grief or reward. Terminal mutation/progression APIs return the unchanged detached state (the gear-organizer command retains its result-object shape). Natural succession carries metadata/history unchanged; fresh same-roster-ID companions remain different people. The whole-life inventory records the existing recovery/time/migration barriers.

A terminal descriptor is derived from validated `battle.mortality` plus `ironman-death`; no full dead save is written to storage. The terminal engine state may be validated as an internal result, but store write/replace/export guards refuse it as a playable save.

## Storage interfaces and commit ordering

**Superseding storage decision, 2026-10-18:** root approved restricted v1 with one independent per-run authority. This replaces the original shared-envelope `ironmanRuns` registry, authoritative-envelope/mirror-refresh and locator/pointer proposals. New Ironman code never writes its full snapshots, floors or locators to the ordinary three-slot envelope or compatibility mirror. No Standard authority migration or general transaction framework is introduced.

`dist/js/ironman-storage.js` supplies detached strict codecs; `dist/js/saves.js` owns transactions. The independent key `hearth-and-oath:ironman-run:v1:<runId>` contains exactly:

```js
{
  version: 1, runId, startedDay,
  revision: '<fresh secure UUID>', updatedAt: '<timestamp>',
  state: latestValidatedPosition,
  casualties: [{ personId, day, battleId, generation }],
  attachment: { slotId, nonce: '<fresh secure UUID>', baseToken }
}
```

`state` plus companion-only `casualties` plus attachment commit in one atomic `setItem` and exact confirmation read. The floor equals the head's validated ledger. A continuation must include the entire prior floor, cannot decrease day/generation or change dynasty identity, and never repairs an older snapshot by injecting deaths. An attachment nonce changes only on new/reviewed attachment; the record revision changes on every accepted mutation. `attachment:null` with a full head means a retained recoverable archive. **True position deletion** writes `state:null, attachment:null` and retains only its floor/identity metadata; this is neither an archive nor a hero-ended marker, and automatic import/recovery into that deleted position is refused in v1.

New/imported/reattached Ironman heads may attach only to a **verifiably empty raw Standard current slot**. The base token binds the exact raw slot object and its existing raw backup, not migrated values or neighboring slots. A nonempty invalid snapshot that migrates to null, unreadable/unknown-version source, or recognized historical shared mortality claim is not empty. An unrelated previous-life backup may remain and is never evicted or rewritten. No one-step Standard-over-Ironman replacement is supported: explicitly archive/delete the Ironman position, then freshly review the revealed underlying Standard slot.

All run keys and ended-marker keys are completely enumerated, read and validated under the same actually entered exclusive lock before ordinary Ironman admission. Missing/inaccessible/incomplete enumeration, unknown/malformed records or standalone marker keys block Ironman authority, not valid ordinary Standard durability. There are no attachment pointer keys. A virtual slot view selects a head only when its exact empty raw base still matches and no other current run claims that same slot/base. Duplicate matching claims block unchanged, never implicitly select a winner. An observed readable occupied/token-mismatched base revokes only that orphan's attachment and retains its full head/floor for explicit recovery. Unreadable/unsupported base inspection blocks unchanged, never infers an orphan; after an already confirmed head write it returns unconfirmed/frozen without a second write. Wrong-slot requests do not revoke a valid attachment. An unobserved transient underlying-token ABA is an admitted limit; it cannot roll back the independent head, floor or ended marker.

The original private Standard slots/observed/backups/unsaved/validation cache remain separate from derived Ironman list/read/health views. A hydrated head must never enter a Standard mutation draft, envelope or mirror serializer. Standard can still save durably without Web Locks and retains its current fallback/rollback rules. An unlocked Standard writer can change the underlying raw slot/backup and orphan the independent Ironman head, but cannot overwrite its full position or floor. Recognized old shared mortality deliberately blocks destructive Standard rewrites rather than silently dropping unknown death knowledge. Ordinary unrelated malformed independent run data does not disable Standard saving.

`createSaveCoordinator().exclusive(operation)` must actually enter the real exclusive Web Lock, without the Standard SecurityError/NotSupportedError fallback. The store captures that implementation privately; a caller boolean, custom coordinator or overwritten public method cannot grant permission. New Ironman creation/play requires usable durable storage and coordination, with no session-only fallback. Every public guarded operation acquires the lock itself; callers do not nest locks.

Guarded APIs return explicit results:

- `inspectIronman(input, {intent, slot, token?, consume?})`: `create`/unknown `import` review binds the raw empty target; `reattach` review binds the current authoritative head and target. `resume`/`export` require a synchronous consumer invoked with a detached head while the same lock is held. Sync display reads/tokens are never reusable adoption/export permission.
- `commitIronman(slot, state, {intent:'create'|'import'|'continue', token, consume?})`: validates current head/base/revision/floor and writes only the one run key. Fresh creation requires a current playable opening, no battle/casualties and `startedDay===day`. Known retained-run import returns `known-head`, never overwrites authority with the supplied JSON, even if its metadata is plausible.
- `listRecoverableIronman()` lists retained archives/observed orphans, not deleted/ended heads. `reattachIronman(runId, slot, {reviewed:true, token})` attaches only that latest head to a freshly reviewed empty base with a new nonce. `archiveIronman` and `deleteIronman` require explicit review/current head token and have the distinct retention semantics above.
- `endIronman(slot, terminal, {token})` validates the current record revision/attachment, exact current hero, unchanged current generation, nonretrograde day and prior floor. If a battle was already stored, its instance and captured policy must match; genuine opening hero death is allowed when the previous head had no battle.

Independent terminal key: `hearth-and-oath:ironman-ended:v1:<runId>` contains only `{version:1, runId, personId, day, battleId}`, no full snapshot/name. Confirm this marker **before** invalidating matching store copies and removing/confirming only that exact run key. Never invoke ordinary `remove` or rewrite shared data. A valid existing marker outranks all head/attachment data and authorizes idempotent exact-key cleanup under the real lock even with an obsolete slot token or unrelated corrupt discovery. Normal adoption still requires complete discovery. Unexpected historical shared full same-run copies are not repaired here: cleanup reports pending rather than falsely claiming all browser-managed full bytes were removed. Marker/record bytes and storage `clear` must invalidate matching session authority in phase 4.

Outcomes distinguish `review`, `ready`, `known-head`, `committed`, `stored-orphan`, `archived`, `deleted`, `ended`, `ended-cleanup-pending`, `blocked`, `stale` and `unconfirmed`. A write may have succeeded even when readback fails: freeze and reconcile/retry against fresh authority, never roll back or declare it definitely uncommitted. Record-write uncertainty never becomes a Standard unsaved/export fallback. Marker failure says durable deletion is unconfirmed; confirmed marker plus cleanup failure says the run is ended but full-byte cleanup remains pending. Creation interrupted before its single write leaves Standard untouched; after it, the complete head/floor is either attached or an intact recoverable orphan. Unrelated slots, backups and compatibility-mirror bytes are untouched by every Ironman mutation.

## App ownership and acceptance boundary

Phase 4A adds small DOM-free `dist/js/ironman-session.js` to own Ironman pending/blocked/ended transaction state and stale command generation. Its `tests/ironman-session.test.js` is authored separately. App/creator/helper integration is **not included** in 4A; no opt-in is exposed. `app.js` remains shell/render/navigation owner. This is not a rewrite of the general app or save store.

The coordinator injects the guarded store, `readContext() -> {state,slot}`, synchronous `onAdopt(state,context)`, matching-run-only `onEnd({runId,marker,cleanupPending})`, lifecycle `onDetach({runId,deleted})` and optional metadata-only `onStatus`. `resume`, `create`, `import`, `accept`, `archive`, `delete`, `reattach`, `recoverCandidate` and `chooseAuthority` reserve synchronously and always return Boolean false, never a truthy Promise. `settled`, `retry` and `refresh` return metadata status only; no candidate/head token is in `status()`. `protect(consume)` invokes the synchronous export/practice consumer under a fresh actual store lock for the unchanged current binding, returning only its explicit value. It cannot adopt a newer head. Store methods are never wrapped in another held `coordinateSave` lock.

### Session state table and reconciliation precedence

| State | Accepted transition | Required disposition |
| --- | --- | --- |
| dormant | Ironman load/admission reserves a request | Standard remains independent; no mode conversion or storage write by this state. |
| ready | One exact-source accepted command reserves before asynchronous persistence | Capture immutable operation ID, source reference, original token and detached candidate. Disable other mutation/navigation/export. |
| pending | Current locked consume confirms a living head, or end confirms a marker | Living adoption/effects occur once; terminal never invokes normal success effects. No playable candidate before confirmation. |
| blocked | Explicit retry/fresh inspection | Retain unresolved candidate/identity/token. No cached-source, Standard-unsaved or export fallback. Different authority remains stale, never relabels an old candidate. |
| ended | Marker-authorized exact-key cleanup retry | Dispose matching full copies; retain tiny run/marker/cleanup metadata only. Unrelated lives survive. |

An operation ID/obligation is separate from the view epoch. Storage/base/clear events or navigation invalidation may freeze adoption and cancel stale presentation effects, but do not cancel a queued operation or clear required live, fatal or first-save retry material. Precedence is **terminal obligation, then reserved live/first-save candidate, then idle probe**. An unchanged durable pre-command head never restores ready while any mutation is unresolved: it may omit a companion casualty or precede hero death. Only an idle probe without an unresolved mutation can restore ready from unchanged displayed authority.

- **Live uncertainty:** compare the authoritative head inside a fresh locked consumer with the exact reserved candidate and original token. Exact candidate permits one authoritative adoption, not another write/engine command/effect replay. Original token permits retry of only that same candidate; `refresh` reports retry-required while explicit `retry` writes through the store's fresh checks. A different head/token stays stale/blocked. No old candidate receives a fresh token. A stored orphan requires separately reviewed recovery and fresh resume, not shared-slot overwrite.
- **Terminal uncertainty:** preserve the original terminal/token across every view invalidation. Retry only the original end request; absent marker still requires original current ownership/hero/day/generation/floor. Matching pre-death head permits only end retry, never resume. Advanced/missing head without a marker stays blocked. Confirmed marker/cleanup-pending clears matching full copies even if the original view epoch is stale. A later retry uses only the run ID through the actual store's existing-marker-first path; that tiny input cannot end a marker-free run.
- **First-save uncertainty:** preserve fixed run ID/candidate/original empty review token until reconciliation after the attempted write settles. Existing authority is preserved/named, never silently overwritten with Standard. Missing head plus unchanged original empty review token permits identical retry. Explicit return to Standard is allowed only after canceled Standard prehistory before any first commit, or a definitive pre-write admission refusal; a generic uncertain/blocked first write is not abandonment permission.
- **Effects and copies:** adoption occurs only while the locked callback, operation ID, source reference and current view epoch agree. `afterAdopt` is once-only and is dropped by view invalidation, not replayed by retry. Late confirmed end always calls matching-run cleanup, never adopts a dead state or erases a newly selected unrelated life. Status snapshots expose only phase/epoch/busy/unresolved/operation kind+ID/run+slot/reason/cleanup metadata.

Additional bounded resolution paths:

- `archive(runId,{reviewed:true,token})`, `delete(...)` and `reattach(runId,slot,{reviewed:true,token})` own their pending lifecycle reservation. Archive/delete never adopt a playable state; matching binding/copies are detached through tiny metadata, while any unrelated binding stays blocked until its own fresh idle verification. Reattach retains its original review token separately from the post-commit expected head token/fingerprint and adopts only through a second fresh locked inspection. Uncertain lifecycle remains blocked. A new explicitly reviewed **same-run lifecycle-only** choice may supersede an earlier archive/delete/reattach obligation; this shortcut cannot replace live/create/import/terminal intent. Every new reservation is validated, including context and slot, before the old obligation is disposed.
- `recoverCandidate(runId,slot,{reviewed:true,token})` is only for same-run unresolved live/create/import that became a stored orphan, never terminal. Preserve original operation ID, candidate and gameplay source token. Attachment review/target are separate parameters. After guarded reattachment, a fresh locked resume resolves only an authoritative head exactly matching the reserved candidate; source/different/missing authority cannot clear the obligation or relabel its gameplay token. Uncertainty retains the original intent.
- `chooseAuthority(runId,slot,{reviewed:true,token})` is the explicit newer-already-saved-position choice after rejected stale action, not undoing accepted death. A fresh same-run locked inspection must match the reviewed current token and prove both token **and full body** differ from the immutable original source before discarding live/terminal intent. Revision-only/no-op source re-save cannot escape a casualty or fatal obligation. Exact nonterminal candidate is the separate one-time adoption path. Marker always wins; unchanged/missing/unreadable authority stays blocked. This never replays the old action or installs its candidate under a new token.

`releaseStandard()` refuses while busy or any mutation obligation remains unresolved. Phase 4A exposes no generic cancel/overwrite/relabel operation. The corresponding reviewed UI choices, exact callback cleanup and app handler fences remain 4B work. Cleanup-only retry may be slotless because the confirmed independent marker, not an original slot, owns exact-key removal; ordinary load/commit still requires a valid slot.

For Ironman only, future `update(next,message,{afterAdopt})` reserves the transition immediately, disables further gameplay/save-affecting commands, captures exact prior position/slot/token and runs the guarded operation in the exclusive lock. It remains Boolean: Standard keeps synchronous adoption/save/render/true; Ironman returns false while pending, not a Promise. Success-dependent gear/craft/trade/note/maze/reply/focus handlers use the deferred callback; false must not trigger gear's current rollback or discard tentative trade/craft drafts. It adopts/renders a playable `next` only after authoritative commit. A stale queued command fails without adopting its computed result. A terminal result follows marker-first purge, clears game/saved/pending import/recovery/unsaved/practice/session copies of that run, and shows a small outcome screen. A failed mortality commit remains frozen with retry and honest copy, not playable export/resume of the pre-death state. Navigation or stale UI controls cannot cancel a queued terminal transaction into resurrection.

All mutation/export/load paths participate, not just `update`: creator acceptance, load/Continue, ordinary save, reviewed import, backup restore, protected-position recovery/retry, notification-read writes currently bypassing `update`, direct game assignment, queued stale actions and storage notifications. Export is rechecked against durable markers/floor under coordination before constructing a playable JSON. Import parses locally but acceptance is rechecked under the lock. Marker events immediately invalidate/stop a matching live run; they do not merely show the ordinary dismissible conflict dialog.

Creator draft defaults to Standard and preserves explicit choice through Back, step changes, rerolls and starting-age changes. The UI states hero save-loss, permanent companion deaths, combat-only exceptions and browser-managed-copy limits before entering. Ironman creation/reattachment targets only a freshly reviewed raw-empty Standard slot; archive retains a recoverable head, whereas true position deletion does not. The session must explicitly adopt its returned slot rather than relying on the unchanged Standard active-slot field. Do not expose this control before the storage/session guard is complete.
