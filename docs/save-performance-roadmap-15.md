# Save-path performance (roadmap 15)

Status: integrated for v0.47.0; controlled save/fresh-store comparisons, the current 88-case focused correctness gate and exact packaged-offline cache/conflict/export checks passed. Publication and non-destructive browser Save/reload verification follow those gates. This is not a browser-performance certification or a change to simulation rules.

## Measured target and narrow change

An initial quiet, one-sample diagnostic on clean source `8adb064c741103ccdce8dbcabee00807a2996398` found that re-migrating unchanged durable lives/backups consumed 621 ms of a 927 ms Node three-slot/three-backup write. This selected a hotspot; one sample is not the release benchmark. Incoming migration remained 112 ms. These are Node CPU measurements with Map-backed storage, not browser/device jank or localStorage disk measurements.

The save store retains one private deep snapshot keyed by the exact authoritative-envelope and compatibility-mirror strings. Each operation still reads both actual durable strings before using it. Any changed bytes take the full existing validation/migration path; incoming writes always validate. Public list/read/backup results and mutation drafts never expose the cached object. Quota/read failures invalidate it, and explicit reload, reviewed replacement and deletion force fresh validation. The cache adds one bounded envelope-sized object graph; it never discards journal or dynasty history.

Revision and deletion tokens, target conflict checking, Web Locks, backup retention, legacy mirrors, strict deletion reviews, rollback and unsaved export remain unchanged. No validation is removed from app actions, new write inputs, imports, or externally changed durable bytes. There is no account, analytics, network transmission, or asset/content pruning.

## Controlled experiment, defined before candidate timings

Run only in a reserved quiet lane, sequentially, using the same Node/environment, fixture materialization and warmup/sample counts. Run baseline and candidate from separate clean checkouts. A report records full source revision and individual JS-module hashes; the comparator permits only `saves.js` to differ.

Fixtures reuse retained generated game people, not human saves or stat-inflated synthetic combat fixtures:

- Three checksum-anchored action-earned age-18 roots from the existing balance evidence, with their distinct worlds.
- A historical age-103 retired scholar, with 576 journal entries, from the checksum-manifested API archive.
- A genuine generation-2 successor with a preserved prior-life chronicle and 273 journal entries from that archive.
- The retained connected v27 journey, age 31 with 957 journal entries and later world topology.
- A fixed-seed newborn and its actually offered first choice generated by the public engine. Optional adult creation uses the actual age-18 generation API, with no granted stats or skipped years.

Older historical cases are explicitly migration/long-history evidence, not a claim about a modern 999-hex multi-generation population. The harness copies all their content intact. Three backups model reviewed replacements and are valid prior lives, not three extra active slots.

Commands from the candidate checkout (substitute absolute checkout paths):

```sh
python3 scripts/prepare-performance-fixtures.py --out=/tmp/hearth-performance-fixtures
node scripts/profile-save-performance.mjs --modules=/absolute/baseline/dist/js --fixtures=/tmp/hearth-performance-fixtures --mode=save --samples=5 --warmups=1 --isolation-note='Reserved sequential quiet lane' --out=/tmp/save-baseline.json
node scripts/profile-save-performance.mjs --modules=/absolute/candidate/dist/js --fixtures=/tmp/hearth-performance-fixtures --mode=save --samples=5 --warmups=1 --isolation-note='Reserved sequential quiet lane' --out=/tmp/save-candidate.json
node scripts/compare-save-performance.mjs --baseline=/tmp/save-baseline.json --candidate=/tmp/save-candidate.json --out=/tmp/save-comparison.json
```

Repeat with `--mode=cold` for fresh-store/title-save preparation. This measures parsing/migration and the initial read/list copies with an already imported engine graph, not full title boot, DOM/CSS/art/media or browser readiness. Cold engine/save import time is separately recorded once per process and has no robust speed claim. Optional `--mode=create` records actual fixed-input adult generation and output identity separately; it is not needed to manufacture the retained adult fixtures.

Predeclared local acceptance: at least three measured samples per graph; identical original/migrated inputs, action outputs, active slot, complete state/backups and mirror payloads; target revision/timestamp advance asserted separately; all untouched slot metadata exact; incoming migration remains mandatory; actual durable reads retained; changed external bytes fully validate. Three-slot/three-backup median writes must improve by at least 20% on this workload. No other write median may worsen by more than max(25 ms, 20%), and no fresh-store median by more than max(50 ms, 20%). These are bounded experiment gates, not promised budgets for every device.

## Paired save result

A reserved, sequential quiet lane compared clean baseline `8adb064c741103ccdce8dbcabee00807a2996398` with clean candidate `ebe3566c1b9892e86fac3e8408e88aa6be26669c`. Every JS module except `saves.js` was byte-identical. Each case had one warmup and three measured samples. All predeclared save-comparison gates passed:

- Adult action write, one slot: median 310.9 → 232.1 ms (25% lower).
- Adult action write, three distinct slots: 599.1 → 323.1 ms (46% lower).
- Adult action write, three slots plus three backups: 871.1 → 397.9 ms (54% lower).
- Reused-store repeated write, three slots plus backups: 865.3 → 388.4 ms (55% lower).
- The three-slot/backup path fell from seven migrations to one incoming-state migration. A changed external neighbor still invoked all four required migrations in both graphs.
- Newborn first commit rose 73.9 → 83.4 ms (9.4 ms / 13%), within the predeclared 25 ms / 20% non-target tolerance. Every other measured save case improved, including the complete age-103, generation-2 and 957-entry cases.

Complete state/input/output hashes, exact backups/mirror and untouched neighbor metadata matched. Changed target revision and timestamp advancement were asserted separately rather than erased from parity. Actual durable reads remained mandatory. The [compact summary](performance/save-paired-three-summary.json) and [complete source-bound reports](performance/save-paired-three.json.gz) retain all samples, input provenance, module hashes and limits.

These results describe only the measured Node save-store workload. They do not establish a 54% improvement to whole browser actions: app validation, simulation, rendering, media, browser storage and device scheduling remain separate work.

## Fresh-store result

A second reserved quiet lane compared the same baseline with clean documentation-only descendant `ef03b6fa9dfb0c0fe1faa419c95f8f5d3daabed9`; its runtime graph is identical to the measured implementation candidate. Three samples plus one warmup passed the predeclared fresh-store gate. Median save/title preparation was 0.04 → 0.06 ms empty, 178.2 → 177.9 ms for one adult, and 819.8 → 855.3 ms for three lives plus backups. The latter 35.5 ms / 4.3% increase is the bounded extra-copy tradeoff, below max(50 ms, 20%). Initial validation counts remain unchanged. See the [cold-store summary](performance/save-cold-three-summary.json) and [complete cold-store reports](performance/save-cold-three.json.gz).

This is not a cold browser/title or device measurement. Full adult-generation timing was not run; the unchanged generation/engine graph does not depend on the save-store module, and no new expensive age-80 fixture was generated for this change. Source equivalence is not a timing certification.
